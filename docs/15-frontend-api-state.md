## Полное покрытие бизнес-API

Все пути API в таблице начинаются с `/api/v1`. Это не адреса страниц React.

| № | Метод и путь | Где используется | Тело / особенности |
|---|---|---|---|
| 1 | POST `/auth/register` | Регистрация | `email`, `password`, `display_name`, `preferred_categories`; 201, без автовхода |
| 2 | POST `/auth/login` | Вход | `email`, `password`; 200 User + cookie |
| 3 | POST `/auth/logout` | Меню аккаунта | Без тела; 204 |
| 4 | GET `/me` | Проверка сессии, профиль | 200 User; отсутствие сессии — 401 |
| 5 | PATCH `/me` | Профиль | Только изменённые `display_name` / `preferred_categories` |
| 6 | GET `/categories` | Фильтры и формы | `{data: [{code, name}]}`, без pagination |
| 7 | GET `/places` | Поиск, карта, admin-список, выбор фильтра истории | Query-параметры поиска; список с pagination |
| 8 | GET `/places/:id` | Карточка, редактор, названия в истории | 200 Place; не создаёт view |
| 9 | POST `/places` | Admin: создание | CreatePlace; 201 Place |
| 10 | PATCH `/places/:id` | Admin: редактирование | `expected_version` + изменённые поля; 200 Place |
| 11 | DELETE `/places/:id?expected_version=N` | Admin: удаление | Без тела; 204 |
| 12 | GET `/me/places/:id/state` | Личные действия в карточке/истории | 200 State, в том числе для удалённого места |
| 13 | PUT `/me/favorites/:id` | Добавить избранное | Без тела; 200 State |
| 14 | DELETE `/me/favorites/:id` | Убрать избранное | Без тела; 200 State |
| 15 | GET `/me/favorites` | Избранное | Только `limit`, `offset` |
| 16 | PUT `/me/ratings/:id` | Поставить/изменить оценку | `{"rating": 5}`; 200 State |
| 17 | DELETE `/me/ratings/:id` | Убрать оценку | Без тела; 200 State, `rating=null` |
| 18 | POST `/interactions` | Просмотр и явный выбор места | `event_key`, `place_id`, `type=view/select`; 201 или 200 replay |
| 19 | GET `/me/interactions` | История | `type`, `place_id`, `limit`, `offset` |

`/health/live` и `/health/ready` проверяем в инфраструктуре и smoke-тестах, не добавляем отдельные кнопки для них в пользовательское меню.

## Сессия и CSRF

Авторизация остаётся через HttpOnly cookie `geoassist_session`. JWT, Bearer token, чтение cookie из JavaScript и хранение токена в localStorage не нужны. Сетевой клиент использует относительные URL и `credentials: 'same-origin'`.

При старте приложения выполняем `GET /me`: 200 даёт текущего пользователя, 401 означает гостя. Сетевой сбой/503 — отдельное состояние «Не удалось проверить вход», а не доказательство отсутствия сессии. Защищённые запросы запускаются только после успешного определения пользователя.

Для POST/PUT/PATCH/DELETE добавляем `X-GeoAssist-CSRF: 1`, включая регистрацию, вход и выход. `Origin` выставляет браузер; frontend не пытается подставлять его вручную. Он должен точно совпадать с `APP_ORIGIN` backend, включая порт. Режимы 8080/5173 описаны в [архитектуре](13-frontend-architecture.md).

Cookie отправляется браузером автоматически в рамках настроенного режима credentials; `fetch` при HTTP-ошибке сам не выбрасывает исключение, поэтому клиент явно проверяет `response.ok`. [MDN: Using Fetch](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch).

После login записываем User в session query, обновляем личные запросы. После подтверждённого logout/204 отменяем личные запросы, очищаем их кэш и переводим session в guest. При ошибке logout не сообщаем ложный успех: предлагаем повторить; HttpOnly cookie вручную не удаляем.

При истечении сессии прекращаем отправку личных событий, очищаем личные данные и предлагаем войти. Публичный каталог остаётся доступен. Для смены аккаунта и повторного входа ведём номер поколения сессии: поздний ответ от старого пользователя не должен восстанавливать его кэш. Сигнал входа/выхода между вкладками можно передавать через BroadcastChannel без персональных данных; получатель заново проверяет `/me`.

## Общий HTTP-клиент

Один `client.ts` отвечает за:

- префикс `/api/v1`, credentials, custom CSRF header;
- `Content-Type: application/json` только при наличии JSON-тела;
- преобразование `204` в отсутствие результата, без попытки прочитать JSON;
- разбор `{data}` и `{data, pagination}`; проверку, что ответ действительно JSON нужной формы;
- типизированную ошибку `status/code/message/details/requestId/retryAfter`;
- `AbortSignal` для отмены устаревших GET и смены сессии;
- различение сетевой ошибки, отменённого запроса и HTTP-ошибки;
- отсутствие тела там, где сервер его запрещает: не отправляем даже `{}` для logout/favorite/delete.

Запросы принимают только известные поля. В API нельзя слать весь React state или все query-параметры URL страницы. Например, UI-переключатель `view=map` не является параметром backend.

Типы генерируем из OpenAPI, но правила форм дополняем вручную: `x-minBytes/x-maxBytes` пароля не равны длине строки JavaScript. При обнаружении расхождения схемы и handlers уточняем контракт, а не обходим серверную проверку.

## Где хранить данные

| Данные | Источник / хранилище |
|---|---|
| Текущий пользователь | `GET /me`, Query cache, session provider как интерфейс доступа |
| Категории, места, избранное, история | TanStack Query |
| Применённые фильтры, offset | URL страницы |
| Ещё не применённые фильтры и редактируемая форма | React Hook Form / локальное состояние |
| Открытое окно, выделенный маркер | Локальное состояние компонента |
| Ключи текущих событий | Память event recorder, ограниченный набор текущих/недавних операций |
| Пароль, cookie | Пароль только в форме до завершения входа; cookie управляет браузер |

Не сохраняем Query cache, пароли и личные данные в localStorage. Начальная версия не имеет offline-очереди записей.

Query keys должны включать все параметры, влияющие на результат:

```text
['session']
['categories']
['places', normalizedSearch]
['place', placeId]
['user', userId, 'place-state', placeId]
['user', userId, 'favorites', {limit, offset}]
['user', userId, 'history', {type, placeId, limit, offset}]
```

Теги перед построением ключа нормализуем и сортируем; `limit/offset` обязательно входят в ключ. Персональные ключи разных пользователей не пересекаются. После login/logout очищаем личные запросы даже при наличии userId в ключе.

Начальные настройки: категории свежие 30 минут, публичные места 30 секунд, личные данные 10 секунд. При возвращении на вкладку перепроверяем session и активные данные; это не должно создавать view-события. Изменения всё равно инвалидируют соответствующий кэш немедленно. Автоматические refetch и retry библиотеки задаём явно, а не полагаемся на defaults. [TanStack Query: Important Defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults).

Для GET допускаем один повтор сетевой/временной 5xx-ошибки; 4xx не повторяем автоматически. Для всех mutations автоматический retry выключен. Исключение — явный повтор конкретного view/select с сохранённым event_key по правилам ниже.

## Обновление экранов после записи

| Действие | Обновляем / инвалидируем |
|---|---|
| PATCH профиля | Session/User, шапка, профиль |
| Favorite/rating | State из ответа; личные favorites и history |
| View/select | History текущего пользователя |
| Create place | Все варианты списка places; новую карточку кладём в кэш |
| Update place | Карточка из ответа; places, favorites с вложенным Place, названия истории |
| Delete place | Убираем карточку из активного кэша; places, favorites и state перечитываем; события истории сохраняем |
| Logout/401 | Отменяем личные запросы, очищаем личный кэш и recorder |

Первую версию делаем без оптимистического сохранения: значение меняется после ответа сервера, а кнопка показывает отправку. Favorite и rating одного места используют общий замок на время mutation, поскольку ответы возвращают весь State. Это предотвращает перезапись новой оценки запоздалым ответом favorite.

При потере ответа на create/update/delete не делаем слепой автоматический повтор. Create не имеет idempotency key: сообщаем неопределённый результат и предлагаем проверить каталог перед повторным созданием. После update/delete сначала перечитываем место; 404 обрабатываем как недоступность, 409 — как конфликт версии.

## Просмотры и выбор места

```json
{
  "event_key": "83b6e8d2-9d36-4d77-8538-f352f5c776d2",
  "place_id": "507f1f77bcf86cd799439011",
  "type": "select"
}
```

UUID создаёт клиент для конкретного действия, не пользователь. Повтор той же отправки использует тот же UUID и тот же payload; следующее самостоятельное действие получает новый ключ.

`view` фиксируем один раз за посещение страницы места, когда активная карточка и сессия уже загружены. Recorder живёт выше компонента страницы: повтор React effect в StrictMode, refetch, обновление state и повторный render используют одну операцию. Новое посещение страницы после ухода/возврата получает новый visit ID; это отличается от ключа записи browser history, который может повторяться при Back.

Recorder хранит операции по `{sessionGeneration, visitId, placeId, type}` с состоянием pending/succeeded/failed. Параллельные попытки одной операции объединяются. При повторе после сетевого сбоя сохраняется event_key. После смены аккаунта предыдущая операция не отправляется от имени нового пользователя.

Для `select` отправка начинается только по кнопке; пока она идёт, второй клик блокируется. При неуспехе показываем «Выбор не сохранён» и возможность повторить ту же операцию. Ошибка записи view не блокирует чтение места, но не выдаётся за успешное сохранение: показываем ненавязчивое сообщение и повтор. Гостевые действия не ставим в очередь для будущего входа.

Favorite/rating генерируют события на backend. Дополнительный POST `/interactions` для них отправлять нельзя. GET карточки, история и admin-редактор сами события не создают.

## Валидация форм

| Поле | Правило текущего backend |
|---|---|
| Email | Допустимый email, 3–254 байта после серверной нормализации |
| Пароль регистрации | 12–72 UTF-8 байта; измерение `new TextEncoder().encode(value).length`; не trim/normalize |
| Пароль входа | Обязателен; не навязываем регистрации новые правила существующим паролям |
| Имя пользователя | 1–80 Unicode code points после trim |
| Предпочтительные категории | Не больше 5, из справочника, без повторов; `[]` очищает |
| Название / описание / адрес места | 1–120 / 1–2000 / 1–300 Unicode code points после trim |
| Теги | До 20, уникальные после trim/lowercase, `^[a-z0-9][a-z0-9_-]{0,31}$` |
| Категория | Код из `/categories` |
| Координаты | Конечные числа, longitude −180…180, latitude −90…90 |
| Радиус | Целое 1–50000 метров |
| Оценка | Целое 1–5; очистка отдельным DELETE |
| PATCH | Хотя бы одно изменённое поле; null запрещён; location заменяется целиком |

Для подсчёта code points используем `Array.from(text).length`, а не обычный `.length`. Поля чисел различают пустое значение и ноль. Ошибки `details` сервера привязываем к соответствующим полям формы. React Hook Form управляет состоянием формы, Zod — её схемой: [RHF](https://react-hook-form.com/get-started), [Zod](https://zod.dev/).

## Как отображать ошибки

| Ошибка | Реакция интерфейса |
|---|---|
| 401 INVALID_CREDENTIALS | Ошибка формы входа; не запускаем глобальный redirect |
| 401 UNAUTHENTICATED | Guest/истёкшая сессия; очищаем личные данные, предлагаем вход |
| 403 FORBIDDEN | «Недостаточно прав», возврат в каталог |
| 403 CSRF_REJECTED | «Не удалось отправить запрос»; диагностический request ID и проверка конфигурации origin; пароль не обвиняем |
| 404 | Место/страница недоступны; у истории сохраняем событие |
| 409 EMAIL_ALREADY_EXISTS | Ошибка поля email |
| 409 VERSION_CONFLICT | Сохраняем черновик, загружаем актуальную версию, пользователь решает повторно |
| 409 IDEMPOTENCY_CONFLICT | Не генерируем новый ключ автоматически; ошибка протокола события |
| 422 | Ошибки полей или общая ошибка формы |
| 429 | Ожидание по Retry-After; кнопка временно недоступна |
| 400/413/415 | Ошибка формата/размера; не бесконечно повторяем запрос |
| 5xx / сеть | Сообщение и повтор, введённые данные не теряются |

Успешный HTTP-ответ не заменяем фиктивным результатом при ошибке JSON. Операции имеют отдельные состояния загрузки: сбой истории не делает весь сайт неработоспособным.
