# 06. Поиск, геоданные и будущие рекомендации

## Assignment #6: обычный поиск

`q` означает префикс **всего названия**, не подстроку, fuzzy search или семантический поиск. Например, `example` находит `Example Coffee`, а `coffee` не находит это название. Такое ограничение нужно явно подписать в будущем UI.

При записи строим name_search: Unicode NFC, trim, lowercase. Для q применяем ту же нормализацию. В MongoDB используем `^` + экранированный пользовательский текст без флага `i`. Пользовательские символы не интерпретируются как регулярное выражение. Стандартный индекс может поддерживать prefix query; реальный план проверяем explain.

Категория — точное совпадение. Теги — `$all`. Удалённые места всегда исключаются. Все фильтры объединяются AND. Стандартная сортировка — name_search ASC, _id ASC.

Сложный полнотекстовый поиск сейчас не нужен. В частности, не проектируем комбинацию `$text` и `$geoNear` как универсальный поиск: эти механизмы имеют ограничения совместного использования. Для MVP префикс имени включается обычным predicate в геозапрос.

## Assignment #6: геопоиск

HTTP принимает именованные поля longitude/latitude; MongoDB adapter преобразует их в GeoJSON Point `[longitude, latitude]`. Радиус — целое число метров от 1 до 50000. Все три параметра обязательны вместе. Отсутствие геопараметров означает обычный каталог, а не геолокацию по IP.

План aggregation:

```text
$geoNear:
  key = location
  near = GeoJSON Point
  spherical = true
  maxDistance = radius_m
  distanceField = distance_m
  query = deleted_at:null + category/tags/name_search filters
$sort: distance_m ASC, _id ASC
$skip: offset
$limit: limit + 1
```

`$geoNear` — первая стадия. Индекс `2dsphere` обязателен. Не ставим limit до применения фильтров. Вторичная сортировка по ID делает порядок равных расстояний определённым. Не округляем distance до сортировки.

Расстояние рассчитывается по сферической модели, а не по автомобильным/пешеходным маршрутам. Адрес хранится для отображения; автоматическое преобразование адреса в координаты не реализуем. Отдельная проверка геопоиска должна использовать заранее выбранные точки внутри/снаружи радиуса с запасом, чтобы не зависеть от округления на самой границе.

## История и обучение

В журнале interactions сохраняются все принятые события. Источник признаков первой версии CF — `user_places` с favorite=true. Отмена избранного сразу меняет текущее состояние, даже если в истории остаётся favorite_added.

Предпочитаемые категории из профиля помогают описать пользователя, но не считаются доказательством collaborative filtering. Оценки и просмотры собираются для дальнейших экспериментов; в первом алгоритме CF они не влияют на сходство, чтобы не вводить произвольные веса раньше времени.

## Final Project: item-based CF

Для каждого активного места i строим множество U(i) пользователей, добавивших его в избранное.

```text
similarity(i,j) = |U(i) ∩ U(j)| / |U(i) ∪ U(j)|
score(u,j) = Σ similarity(i,j), для i из актуального избранного F(u)
```

Пустое объединение даёт 0. Пользователь учитывается в множестве один раз. Сходство — по поведению пользователей, а не по совпадению категорий. Самосходство не используется.

Получение рекомендаций:

1. Загрузить актуальное избранное пользователя, исключить удалённые места.
2. Собрать кандидатов с положительным сходством и просуммировать score.
3. Удалить уже избранные и логически удалённые места.
4. Применить category/tags/георадиус как жёсткие ограничения.
5. Отсортировать score DESC, затем distance ASC при геопоиске, затем ID ASC.
6. Ограничить результат limit.

После фильтров может остаться меньше limit. Не заменять строгий радиус расширенным автоматически. Если CF-кандидатов нет, использовать popularity fallback с теми же ограничениями и исключением избранного. Популярность — число различных пользователей, у которых место сейчас в избранном; при равенстве distance ASC (если есть), затем ID ASC. score fallback — это количество пользователей, не CF-сходство. Не смешиваем баллы двух алгоритмов в одной выдаче.

## Расчёт модели и оптимизация

Для учебного объёма сначала реализовать прозрачный точный расчёт Жаккара в Go. Запускать отдельной командой построения модели, а не вычислять все пары на каждом HTTP-запросе. На файнале можно хранить текущую модель в памяти одного процесса; после перезапуска она строится до готовности recommendation endpoint. Точную стратегию загрузки модели закрепить при реализации файнала.

Следующий шаг при росте данных — предварительно построенные top-K соседей. Это приближение: его качество сравнить с точным вариантом. Если нужна сохраняемая модель, добавить производную коллекцию соседей с model_version и built_at; основные users/places/user_places/interactions при этом не меняются. Описать такое добавление как производную оптимизацию, сохранив базовую модель задания.

Модель — снимок данных на момент построения. Новые взаимодействия отражаются в сходствах только после rebuild; актуальное избранное и удаление мест фильтруются на каждом запросе. API сообщает model_built_at. Не обещаем мгновенное переобучение. Кэш рекомендаций, если появится, должен учитывать пользователя, модель, фильтры и изменение избранного; для MVP лучше обойтись без него.

## Проверка качества и производительности

- Ручной маленький пример A/B/C с известными множествами пользователей и точными коэффициентами.
- Новый пользователь, пустое избранное, отмена избранного, удалённое место, пустой радиус, одинаковые scores.
- Для необязательной оценки качества использовать отложенные взаимодействия: не обучать модель на проверяемых избранных местах. На синтетических данных результат иллюстративный, не доказательство качества на реальных пользователях.
- Отдельно измерять время построения модели и задержку API; учитывать использование памяти.
- Обязательные для файнала измерения масштабирования и оптимизации описаны в документе 07.

## Связь с будущим NLP

Будущий parser принимает текст и выдаёт строго типизированный SearchIntent: category, tags, radius, optional explicit location. Неоднозначное «рядом» без геолокации требует уточнения, а не выдуманных координат. Application преобразует intent в тот же PlaceQuery и применяет те же пределы и валидацию. Прямое выполнение MongoDB-кода, сгенерированного моделью, не предусматривается.
