# 07. Реализация, запуск и проверка

## Конфигурация

Конкретные версии Go, MongoDB, Gin и driver закрепить в go.mod/go.sum и image tags при реализации. Не использовать плавающий latest в воспроизводимом окружении.

| Переменная | Назначение / локальное значение |
|---|---|
| APP_ENV | development / production |
| HTTP_ADDR | :8080 |
| APP_ORIGIN | http://localhost:8080 |
| MONGO_URI | Строка подключения к replica set rs0; секрет при включённой аутентификации |
| MONGO_DATABASE | geoassist |
| COOKIE_SECURE | false только для development HTTP |
| LOG_LEVEL | info |

Константы первой версии: session TTL 7 суток, bcrypt cost 12, request body 64 KiB, максимальный радиус 50000 м. Если делаем их настраиваемыми, валидируем пределы при старте и отражаем изменения в документации.

`.env.example` содержит примеры без реальных секретов; `.env` в .gitignore. Не записывать пароли или URI с credentials в журнал. Геокоординаты в query также не логировать целиком: журналирует route template, не raw URL.

## Локальный запуск

План Compose: MongoDB single-node replica set → init replica set → migrate → api. Readiness должна дождаться writable primary и применённой схемы. Приложение и MongoDB находятся в одной docker network; hostname replica set должен разрешаться из контейнера приложения.

В основном сценарии MongoDB не публикуется наружу, API доступен на localhost:8080. Если нужен Compass, отдельно документировать loopback-порт и корректный URI для локального подключения; не копировать внутренний hostname без объяснения.

Команды и Makefile/PowerShell helper создавать после реализации, не выдавать описанный порядок за уже работающие команды. Независимые команды migrate/seed/create-admin запускаются в той же сети и с той же конфигурацией, что приложение.

## Seed

Начальный набор: один город, 100 мест, 50 пользователей, несколько пересекающихся групп интересов. Координаты должны лежать в выбранной области; данные явно синтетические.

- Фиксированный seed генератора; одинаковые исходные параметры дают одинаковые ID и связи.
- Seed предназначен для demo-базы; повтор не дублирует документы и не перезаписывает пользовательские правки молча.
- Контракт начального seed: places/user_places/interactions должны быть пусты, в users допустим только заранее созданный admin. Иначе команда прекращает работу с объяснением. Существующий admin сохраняется и становится created_by демонстрационных мест. Для воспроизводимых прогонов выбирать новую отдельную demo-базу и сначала создать admin.
- Не делать автоматический dropDatabase при старте или seed.
- Для синтетических пользователей использовать отдельные известные demo-credentials, обозначенные только для локального стенда. Пароли всё равно хешируются.
- Данные создаются через бизнес-сценарии или общий проверяемый seed service, чтобы состояние и история не расходились.
- Admin создаётся отдельной командой, не обычным public register.

## Наблюдаемость и работа процесса

- Структурированные логи через slog: request_id, method, route template, status, duration_ms; при необходимости user_id, без тел auth-запросов и cookies.
- Ограничение времени HTTP-запроса: начальный budget 10 секунд; MongoDB server selection timeout 3 секунды. Конкретные server ReadHeader/Read/Write/Idle timeouts настроить явно.
- Request context передаётся в MongoDB и прекращает работу после отмены запроса.
- Graceful shutdown: прекратить приём, дать текущим запросам до 10 секунд, закрыть MongoDB client.
- На неожиданную ошибку — 500 с request ID; детали в серверном логе.
- При недоступности БД — readiness 503; защищённые запросы не должны превращать сбой БД в «неверный пароль».

## Проверки по рискам

| Уровень | Что проверить |
|---|---|
| Domain/application | Валидацию координат, правила rating, no-op избранного, права ролей |
| Application | Отсутствие возможности выбрать чужого user_id; ошибки бизнес-сценариев |
| Mongo integration | Unique email и пара user/place, транзакционный rollback, гонку первых вставок состояния |
| Mongo integration | Версии Place, soft delete, фильтрацию до пагинации, схему validator |
| Geo integration | Точки внутри/снаружи радиуса, порядок координат, category/tag/name AND-фильтры |
| Auth integration | Login/logout/expiry, TTL не заменяет проверку, запрет чужого Origin и пропущенного CSRF header |
| HTTP | Форматы body/query, null против отсутствия, JSON errors, 401/403/404/409/422 |
| Activity | Replay event_key, другой payload с тем же ключом, отсутствие дубля событий у повторного PUT |
| End-to-end | Зарегистрироваться → войти → найти место → сохранить → оценить → посмотреть историю → выйти |

Интеграционные проверки работают с реальной тестовой MongoDB replica set, а не только mocks. Rollback проверяем искусственным отказом записи события после изменения состояния: состояние не должно измениться. Конкурентные операции проверяем параллельными запросами. Пароли/хеши/токены не должны появляться в JSON User.

Для документации на текущем этапе проверяются ссылки, согласованность контрактов и синтаксис JSON-примеров. Тесты приложения будут написаны и запущены при появлении реализации; сейчас они не считаются пройденными.

## План реализации Assignment #6

1. Каркас проекта, конфигурация, router, error mapper, request IDs, Docker replica set.
2. MongoDB migrations: валидаторы и индексы; health endpoints.
3. Identity: регистрация, хеширование паролей, сессии, CSRF, профиль, admin CLI.
4. Catalog: модель, CRUD, version conflict, soft delete.
5. Search: префикс, категория, теги, георадиус, пагинация.
6. Activity: user_places, транзакции, избранное, оценки, view/select и история.
7. Seed, интеграционные проверки и демонстрационный API-сценарий.
8. OpenAPI, инструкция запуска, proposal и отчёт со скриншотами.

На первом этапе OpenAPI описываем постепенно вместе с handlers, не оставляем синхронизацию всех маршрутов на последний день. Веб и recommendations не блокируют сдачу шестого задания.

## Definition of Done для Assignment #6

- Проект запускается по документированной инструкции в чистом demo-окружении.
- Реализованы все маршруты текущей версии API; будущий маршрут рекомендаций не выдаётся за готовый.
- Данные сохраняются после перезапуска приложения.
- Нельзя менять каталог обычным пользователем или чужие предпочтения.
- Геопоиск и актуальное состояние избранного демонстрируются тестами и примерами.
- Proposal содержит сравнение моделей NoSQL, индексы, CF-план и связь с диссертацией на 0,5–1 страницу.
- Отчёт включает номер/название, цели, фактические скриншоты и источники.

## Final Project: измерения

Подготовить несколько наборов, например 100/1000/10000 мест с явно зафиксированным числом пользователей и взаимодействий. Размеры — предложение для эксперимента, не требование задания. Указать аппаратное окружение, версии, warm-up, длительность, concurrency и seed.

Сравнивать один и тот же сценарий до/после индекса или кэша: p50/p95, throughput, долю ошибок, число просмотренных документов/ключей из explain, время rebuild модели и память. Не сравнивать разные наборы данных как доказательство эффекта одной оптимизации. Отдельно измерить чтение готовых рекомендаций и построение модели. Не писать вымышленные числа до запуска эксперимента.

## Не входит в текущую реализацию

Полноценный NLP, подключение мессенджера, маршрутизация по дорогам, геокодинг, импорт внешнего каталога, email verification, reset password, загрузка файлов, микросервисы, распределённый кэш. При необходимости это отдельные изменения с обновлением API и модели.
