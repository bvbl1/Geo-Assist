## 1. Концепция и связь с диссертацией

**GeoAssist: платформа геопространственного поиска и персонализированных рекомендаций мест для диалогового помощника.**

Тема диссертации: «Разработка алгоритма перевода запросов на естественном языке в геопространственные запросы в мессенджере».

Платформа позволяет искать кафе, парки, библиотеки, коворкинги и достопримечательности по названию, категории, характеристикам и расположению. Она хранит профили пользователей и их взаимодействия с местами. На этапе Final Project добавляются персональные рекомендации.

Проект реализует слой данных и выполнения геозапросов для будущего помощника. Позднее к нему подключаются модуль перевода естественного языка в структурированные параметры и интерфейс мессенджера.

Пример будущего сценария:

> Найди кофейню с Wi-Fi в пределах двух километров от меня.

Модуль разбора выделяет категорию `cafe`, тег `wifi` и радиус `2000` метров. Координаты поступают отдельно из отправленной геолокации или выбранной точки. Бэкенд выполняет поиск, а рекомендательный модуль может ранжировать подходящие места по предпочтениям пользователя.

Полноценный NLP и интеграция с мессенджером не входят в обязательный объём Assignment #6. Простой разбор шаблонных фраз возможен после выполнения основных требований, но не должен описываться как законченный алгоритм диссертации.

## 2. Решение по стеку

| Компонент | Выбор |
|---|---|
| База данных | MongoDB |
| Бэкенд и REST API | Go + Gin |
| Доступ к базе | Официальный MongoDB Go Driver |
| Рекомендательный алгоритм | Go, внутри того же приложения |
| Веб-интерфейс | Go `html/template`, HTML/CSS и небольшой JavaScript |
| Локальный запуск | Docker Compose |
| Документация API | OpenAPI и примеры запросов |

MongoDB прямо разрешена требованиями Assignment #6. Она поддерживает GeoJSON, индекс `2dsphere` и геопространственный поиск. Collaborative filtering не требует графовой базы: взаимодействия хранятся в MongoDB, а сходство и рекомендации вычисляются в Go.

Neo4j не используем: обходы графа не являются центральной задачей проекта. В proposal сравним документную, графовую и key-value модели применительно к нашим запросам, объяснив выбор MongoDB.

Сохраняем одно Go-приложение с внутренними модулями авторизации, каталога, поиска, взаимодействий и рекомендаций. Отдельный React-проект и отдельный ML-сервис на старте не нужны.

## 4. Базовая модель данных

| Коллекция | Основные данные | Назначение |
|---|---|---|
| `users` | Email, хеш пароля, имя, профиль, роль, дата создания | Аккаунты и профили |
| `places` | Название, описание, категория, теги, GeoJSON-координаты, дополнительные атрибуты | Каталог и геопоиск |
| `interactions` | `user_id`, `place_id`, тип действия, время, оценка при наличии | История и данные для collaborative filtering |

Историю храним отдельно от пользователей, чтобы документы профилей не росли без ограничений. Связи между пользователями и местами представлены идентификаторами в `interactions`.

Пример расположения места:

```json
{
  "name": "Example Coffee",
  "category": "cafe",
  "tags": ["wifi", "quiet"],
  "location": {
    "type": "Point",
    "coordinates": [76.8897, 43.2389]
  }
}
```

Порядок координат GeoJSON: **долгота, широта**. Расстояния в API задаём в метрах. Пример места вымышленный.

Предварительные индексы:

- Уникальный индекс по нормализованному email пользователя.
- `2dsphere` по `places.location`.
- Индекс по категории для соответствующих запросов каталога.
- Составной индекс по `user_id` и времени для истории.
- Индекс по `place_id` для выборок взаимодействий с местом.
- Индексы для избранного и расчёта сходства уточнить по фактическим запросам.

Семантику поиска по названию определить до выбора индекса: префиксный и полнотекстовый поиск требуют разных решений. Не предполагать, что произвольный поиск подстроки будет эффективно использовать обычный индекс.

При реализации определить семантику отмены избранного и изменения оценки. Для рекомендаций использовать актуальное множество избранных мест, а не считать повторные события независимыми предпочтениями.

## 5. Предварительный API

Имена маршрутов можно уточнить при реализации, сохранив функциональность.

| Метод и маршрут | Назначение |
|---|---|
| `POST /api/auth/register` | Регистрация |
| `POST /api/auth/login` | Вход |
| `GET /api/me` | Текущий профиль |
| `PATCH /api/me` | Изменение профиля |
| `GET /api/places` | Каталог и поиск с фильтрами и пагинацией |
| `GET /api/places/:id` | Карточка места |
| `POST /api/places` | Создание места |
| `PATCH /api/places/:id` | Изменение места |
| `DELETE /api/places/:id` | Удаление места |
| `POST /api/interactions` | Запись взаимодействия |
| `GET /api/me/interactions` | История текущего пользователя |
| `GET /api/me/recommendations` | Персональные рекомендации — этап Final Project |

Идентификатор пользователя для защищённых операций берётся из авторизации. Пароли хранятся только в виде подходящих парольных хешей. Конкретный механизм сессий или токенов выбрать при реализации.

## 6. Демонстрационные данные

Начальный ориентир: один город, 100 мест и 50 тестовых пользователей. Это проектное предложение, а не численное требование преподавателя.

Разрешено использовать синтетические данные. Генератор должен создавать пересекающиеся группы интересов: например, любители кофеен, парков и мест для работы. Полностью случайные взаимодействия плохо демонстрируют collaborative filtering.

Сохранять воспроизводимость генерации и явно обозначать синтетический характер данных. Позднее подготовить увеличенные наборы для измерений производительности.

## 7. Рекомендации на Final Project

Основной алгоритм: **item-based collaborative filtering по избранному**.

1. Получить для каждого места множество пользователей, у которых оно находится в избранном.
2. Рассчитать сходство мест по коэффициенту Жаккара: размер пересечения множеств пользователей, делённый на размер их объединения. При пустом объединении считать сходство нулевым.
3. Для пользователя найти кандидатов, похожих на его избранные места.
4. Рассчитать балл кандидата, например суммой сходств с избранными местами пользователя.
5. Исключить места, уже находящиеся в его избранном.
6. Применить ограничения запроса по категории, характеристикам и расстоянию.
7. Вернуть лучшие результаты со стабильным правилом разрешения равных баллов.

Сходство основано на поведении пользователей, а не на совпадении описаний или категорий. Географические фильтры дополняют collaborative filtering, но не заменяют его.

Для новых пользователей и случаев отсутствия подходящих CF-кандидатов предусмотреть популярные места рядом. Такой результат обозначать как запасной вариант, а не выдавать за персональную collaborative filtering.

Начать с понятной реализации в Go. При росте данных рассмотреть предварительный расчёт сходств, хранение только top-K соседей и кэширование. Не пересчитывать все пары мест на каждом пользовательском запросе.
