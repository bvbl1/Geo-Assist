# Assignment #6 — Project Proposal

## GeoAssist: геопространственный поиск и персональные рекомендации мест

**Учебная дисциплина:** базы данных.  
**Задание:** Designing the data layer and backend for a NoSQL recommendation platform.  
**Технологии:** Go, Gin, MongoDB, Docker Compose.  
**Этап:** бэкенд Assignment #6; рекомендательный алгоритм и веб-интерфейс планируются для Final Project.

## 1. Цель и предметная область

Цель проекта — разработать слой данных и API для платформы поиска городских мест, который можно продолжить до рекомендательной системы и затем использовать в исследовании диалогового геопространственного помощника.

Пользователи выбирают кафе, парки, библиотеки, коворкинги и достопримечательности. Объект рекомендации — отдельное место с координатами. Взаимодействия — просмотр, выбор места, добавление в избранное, отмена избранного и оценка. Администратор управляет каталогом; обычный пользователь читает каталог и управляет собственными предпочтениями.

Основные задачи Assignment #6: регистрация и вход, профили, CRUD мест, поиск по названию/категории/тегам, поиск в радиусе, сохранение истории и текущих предпочтений, демонстрационные данные, документация API и воспроизводимый запуск. Реализация рекомендательного алгоритма относится к Final Project.

## 2. Relevance to the dissertation

Тема магистерской диссертации — «Разработка алгоритма перевода запросов на естественном языке в геопространственные запросы в мессенджере». Центральная исследовательская задача заключается в переходе от сообщения пользователя, содержащего намерение и пространственные ограничения, к корректному исполняемому запросу. Например, фраза «найди тихую кофейню с Wi-Fi в пределах двух километров от меня» должна быть представлена через категорию объекта, требуемые характеристики, радиус и исходные координаты. Для проверки такого алгоритма необходима работающая среда, в которой структурированный запрос можно выполнить и получить проверяемый результат.

GeoAssist создаёт такую основу. Каталог хранит географические точки и атрибуты мест, а API принимает строго определённые параметры поиска. Расположение задаётся координатами longitude/latitude; радиус измеряется в метрах. Поиск возвращает объекты, удовлетворяющие указанным ограничениям, и расстояние до них. Благодаря этому будущий модуль обработки естественного языка можно подключить как отдельный адаптер: он формирует типизированное представление запроса, после чего используются уже существующие правила проверки и выполнения поиска. Произвольный текст или сгенерированный код базы данных напрямую не исполняется.

Разделение алгоритма интерпретации сообщения и выполнения геозапроса важно для экспериментальной части диссертации. Оно позволит независимо проверять правильность извлечения категории, характеристик и пространственных параметров, а затем сопоставлять итоговую выдачу с заранее заданными ожидаемыми результатами. Например, для набора контрольных фраз можно подготовить эталонные структурированные запросы и измерить совпадение извлечённых параметров. Корректность самого геопоиска отдельно проверяется на точках внутри и вне заданного радиуса. Так ошибки языкового разбора не смешиваются с ошибками хранения координат и выполнения запросов.

История взаимодействий дополнительно создаёт основу для изучения персонализации. Пользовательский запрос определяет обязательные ограничения, а предпочтения могут определять порядок подходящих результатов. На Final Project этот аспект будет реализован через collaborative filtering по избранным местам. Персонализация не должна нарушать явно заданные пространственные ограничения: объект за пределами указанного радиуса не становится допустимым только из-за высокого рекомендательного балла. Такое разделение позволяет рассматривать геопространственный поиск и рекомендации как последовательные компоненты будущего помощника.

Для демонстрации используются синтетические данные по Астане, что позволяет воспроизвести одинаковые сценарии без сбора персональных геоданных реальных пользователей. Эти данные пригодны для функциональных проверок и первоначальных измерений производительности, но не доказывают качество алгоритма на реальных диалогах и предпочтениях. Полноценный языковой алгоритм, его исследовательская оценка и интеграция с мессенджером выходят за рамки Assignment #6. Результатом текущего задания является переиспользуемая экспериментальная инфраструктура, а не завершённая диссертационная система.

## 3. Выбор NoSQL и сравнение моделей

| Модель / пример | Преимущества для проекта | Ограничения и компромиссы |
|---|---|---|
| Документная / MongoDB | Представление карточки места одним документом; GeoJSON и 2dsphere; фильтры, индексы и aggregation; поддержка транзакций | Нет внешних ключей; связи и бизнес-инварианты требуют проверок; для согласованного состояния и журнала нужны транзакции |
| Графовая / Neo4j | Естественное представление связей пользователь–место; удобство обходов связей | Основной сценарий проекта — поиск объектов и их характеристик по координатам; графовые обходы не являются обязательной частью выбранного CF |
| Key-value / Redis | Подходит для быстрого доступа по ключу и будущего кэша | Для каталога с комбинациями атрибутов и истории потребовалось бы отдельно проектировать дополнительные структуры и индексацию |

Выбрана MongoDB, поскольку её документная модель и геопространственные операторы соответствуют основным запросам проекта. Collaborative filtering выполняется в Go по данным взаимодействий, поэтому выбор графовой базы не является условием реализации рекомендаций. На учебном этапе один процесс приложения и одна база уменьшают сложность развёртывания.

## 4. Модель данных и индексы

| Коллекция | Назначение | Ключевые индексы |
|---|---|---|
| `users` | Профиль, нормализованный email, хеш пароля, роль | Уникальный email |
| `sessions` | Хеш сессионного токена и срок действия | Уникальный token_hash; TTL по expires_at |
| `places` | Название, описание, категория, теги, адрес, GeoJSON Point | 2dsphere по location; индексы каталога по имени и категории |
| `user_places` | Текущее избранное и оценка пары пользователь–место | Уникальная пара user_id/place_id; индексы избранного и выборки пользователей места |
| `interactions` | Неизменяемая история принятых действий | Уникальная пара user_id/event_key; история по пользователю и времени |

Дополнительная техническая коллекция `app_meta` содержит маркер версии импортированного демонстрационного набора. Она не заменяет бизнес-сущности.

Документы разных коллекций имеют разные схемы; внутри каждой коллекции действуют валидаторы типов и обязательных полей. Ссылки хранятся как ObjectID. Координаты GeoJSON имеют порядок `[longitude, latitude]`. История не встраивается в профиль, чтобы размер документа пользователя не рос с каждым действием.

Текущее состояние предпочтений отделено от событий. Повтор добавления в избранное не создаёт новое предпочтение, а отмена немедленно отражается в `user_places`. Изменение состояния и его событие выполняются одной транзакцией. MongoDB запускается как одноузловой replica set, необходимый для выбранного применения транзакций. Такой локальный стенд не является конфигурацией высокой доступности.

Каталог исключает логически удалённые места; история сохраняется. Версия документа места защищает от потери изменений при одновременном редактировании. Поиск по названию ограничен нормализованным префиксом, что даёт понятную семантику и допускает использование обычного индекса. Геопоиск использует `$geoNear`; категория, теги и имя применяются до ограничения выдачи. Эффективность конкретных сочетаний фильтров нужно подтверждать через explain и измерения, а не наличием индексов как таковых.

## 5. Архитектура и API

Приложение — модульный монолит с Clean Architecture. Модули `identity`, `catalog` и `activity` разделяют доменные правила, сценарии использования, HTTP-адаптеры и MongoDB-адаптеры. Домен не зависит от Gin и BSON. Внешние DTO, бизнес-модели и документы хранения разделены.

REST API `/api/v1` предоставляет регистрацию, вход, профиль, каталог, поиск, избранное, оценки и историю. Авторизация использует серверные сессии и HttpOnly cookie. Изменения каталога доступны роли admin, пользовательские предпочтения — только владельцу. Для изменяющих запросов применяются проверки Origin и дополнительного заголовка; API имеет единый формат ошибок и ограниченную пагинацию. Подробные тела запросов и ответов приведены в [контракте API](04-api.md).

В Assignment #6 клиентом для демонстрации выступает Postman. Веб-интерфейс будет добавлен на Final Project и будет использовать тот же API и сценарии приложения.

## 6. Демонстрационные данные и воспроизводимость

Набор содержит 100 вымышленных мест в районе Астаны, 50 обычных пользователей и одного администратора, 400 текущих состояний пользователь–место и 1200 событий. Группы пользователей имеют пересекающееся избранное, чтобы будущий алгоритм мог обнаруживать закономерности совместного выбора.

При первом запуске приложения в демонстрационном режиме данные и маркер версии импортируются одной транзакцией. Повторный обычный запуск с существующим маркером не дублирует записи и не перезаписывает пользовательские изменения. При отсутствии маркера и наличии посторонних бизнес-данных импорт прекращается с объяснением; уничтожения существующей базы нет. В рабочем окружении автоматический демонстрационный импорт отключается.

## 7. План рекомендаций для Final Project

Планируется item-based collaborative filtering. Для каждого места формируется множество пользователей, у которых оно сейчас в избранном. Сходство двух мест определяется коэффициентом Жаккара: размером пересечения этих множеств, делённым на размер объединения. Балл кандидата для пользователя — сумма его сходств с местами из текущего избранного пользователя.

Из кандидатов исключаются уже избранные и удалённые места, затем применяются пространственные и атрибутивные ограничения. При отсутствии CF-кандидатов используется явно обозначенный запасной вариант — популярные места с теми же ограничениями. Популярность и близость сами по себе не выдаются за collaborative filtering.

Первые эксперименты используют прозрачный точный расчёт в Go. Далее возможны предварительный расчёт top-K соседей и кэширование. На файнале нужно измерить задержки API, пропускную способность, время построения модели и использование ресурсов на увеличивающихся наборах данных. Полученные числа и результаты оптимизации фиксируются только после фактического выполнения эксперимента.

## 8. Проверка и ожидаемые результаты

Критерии готовности Assignment #6: воспроизводимый запуск Docker-окружения, сохранение данных, работа всех согласованных API-маршрутов, корректное разграничение прав, поиск в радиусе, согласованность предпочтений и истории, документация и демонстрационные запросы.

План проверки включает unit-тесты правил и интеграционные тесты на реальной MongoDB: rollback транзакции, конкурирующее добавление избранного, повторную запись событий, конфликт версии и фильтрацию удалённых мест до пагинации. Этот proposal описывает проект и критерии, а не утверждает, что все перечисленные проверки уже выполнены. Фактический статус проверок и демонстрационные материалы приводятся в итоговом отчёте.
