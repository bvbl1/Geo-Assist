# 05. Авторизация и права

> Реализация готова: актуальные команды в [README](../README.md). По запросу пользователя при старте добавлен одноразовый импорт демоданных Астаны вместе с demo admin. Техническая коллекция app_meta хранит маркер импорта. Основной compose.yaml расположен в корне. Ниже сохранены проектные решения с уточнениями реализации.


## Выбранный механизм

Серверные сессии в MongoDB и HttpOnly cookie. Это подходит одному приложению, которое обслуживает и API, и будущий веб. Не добавляем JWT, refresh tokens и OAuth для учебного MVP.

1. Пользователь проходит POST login.
2. Сервер генерирует 32 криптографически случайных байта через `crypto/rand`, кодирует base64url без padding.
3. В `sessions` сохраняются SHA-256 токена в hex, user_id, created_at и expires_at (now + 7 суток).
4. Исходный токен передаётся только через Set-Cookie.
5. Middleware хеширует cookie, ищет сессию и проверяет expires_at; загружает пользователя и текущую роль.
6. Application получает Actor, не cookie или MongoDB-документ.

Срок фиксированный, без sliding expiration. Каждое успешное выполнение login создаёт новую сессию. Если у запроса уже есть действующая cookie, старую сессию этого браузера отзываем вместе с созданием новой в транзакции; сессии других устройств сохраняются. Auth-проверка и запись cookie выполняются после успешного commit. Не принимаем пользовательский session ID для новой сессии.

## Cookie

Рабочее имя: `geoassist_session`. Параметры: `HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age=604800`, без Domain (host-only). В HTTPS-окружении обязательно `Secure=true`. Для локальной демонстрации `http://localhost:8080` допускается `Secure=false` только при APP_ENV=development. При запуске production с HTTP origin или отключённым Secure приложение отказывается стартовать.

Logout удаляет сессию и отправляет cookie того же имени/Path с Max-Age=0 и истёкшим Expires. Истечение проверяет приложение: TTL-удаление происходит не мгновенно. Содержимое cookie, токены, password_hash и пароли не логируются.

## CSRF и CORS

Предполагаем веб и API одного origin, например `http://localhost:8080`.

Для каждого POST/PUT/PATCH/DELETE, включая public login/register и запросы без тела:

- Требовать заголовок `Origin`, точно равный настроенному `APP_ORIGIN` по scheme/host/port. Значения `null`, отсутствующее значение и другой origin отклонять 403.
- Требовать нестандартный заголовок `X-GeoAssist-CSRF: 1`. Это маркер для защиты от простых cross-site запросов, не секретный токен.
- Для JSON-запросов проверять Content-Type; не принимать form-urlencoded/text/plain как JSON.
- Не включать cross-origin CORS и не разрешать credentialed-запросы сторонних origins. Не отражать произвольный Origin.
- Использовать SameSite как дополнительную защиту, а не единственную проверку.

Web отправляет такие запросы через `fetch` с custom header; обычные HTML form POST без адаптации не являются поддержанным клиентом. Postman/curl должны явно указывать Origin и custom header. Это осознанный контракт для MVP. Если позднее появится отдельный origin фронтенда или мессенджер, механизм доступа проектируется отдельно, проверки просто не отключаются.

Пример HTTP-входа локально (пароль демонстрационный):

```http
POST /api/v1/auth/login HTTP/1.1
Host: localhost:8080
Origin: http://localhost:8080
X-GeoAssist-CSRF: 1
Content-Type: application/json

{"email":"student@example.com","password":"demo-password-2026"}
```

Следующие запросы отправляют cookie из ответа. На GET custom header и Origin не обязательны.

## Роли и создание администратора

| Действие | Anonymous | User | Admin |
|---|---|---|---|
| Категории, каталог, поиск, карточка | Да | Да | Да |
| Собственный профиль, состояние, история | Нет | Да | Да |
| Собственное избранное и оценки | Нет | Да | Да |
| Создание/редактирование/удаление мест | Нет | Нет | Да |
| Назначение роли через публичный API | Нет | Нет | Нет |

В development с AUTO_SEED=true demo admin создаётся импортом (credentials в README). Дополнительный admin создаётся отдельной командой create-admin: email и имя — параметры, пароль — интерактивный скрытый ввод. Никаких стандартных admin/admin и передачи пароля аргументом командной строки. При занятом email команда завершается ошибкой, а не повышает роль существующего пользователя молча.

Actor.UserID определяется по сессии. Клиент не выбирает пользователя через JSON или query. Authorize-проверки выполняются и в application для будущих транспортов.

## Пароли и ограничения

Для MVP используем `golang.org/x/crypto/bcrypt`, начальная стоимость 12; измерить задержку при реализации. Ограничение длины — 12..72 UTF-8 байта. Соль генерирует библиотека. Пароли не trim/lowercase. Сравнение выполняет bcrypt, а не сравнение строк хешей.

Неверный пароль и неизвестный email возвращают одинаковую ошибку. Для отсутствующего пользователя выполнять сравнение с заранее подготовленным фиктивным хешем, чтобы не создавать явную разницу по времени вычисления.

Планируемые начальные лимиты (проверить нагрузочным тестом): login — 10 попыток/мин/IP и 10/мин/нормализованный email; register — 5/час/IP; запись view/select — 60/мин/user. Ограничители в памяти допустимы при одном процессе; их состояние теряется при перезапуске. Указать это ограничение в отчёте. Не доверять X-Forwarded-For от неизвестного proxy.

Reset password, email verification, изменение email и внешняя авторизация вне MVP. Веб выводит пользовательские строки через стандартное escaping `html/template`, не через trusted HTML.
